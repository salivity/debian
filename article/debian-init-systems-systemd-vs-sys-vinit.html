Debian Init Systems: systemd vs SysVinit

This article compares how the Debian operating system handles system initialization under the modern systemd suite versus the legacy SysVinit system. It examines the architectural shift from sequential shell scripts to concurrent unit files, exploring key operational differences in boot performance, service management, process tracking, and backward compatibility.

Architectural Foundations

Debian historically relied on SysVinit, a traditional Unix initialization scheme that models system startup through rigid runlevels (numbered 0 through 6). Initialization is driven by shell scripts residing in /etc/init.d/, which are symlinked into runlevel directories (/etc/rcX.d/) using a naming convention that dictates execution order (e.g., S01 to start, K01 to kill).

In contrast, systemd approaches system state through a declarative dependency graph. It replaces runlevels with "targets" (such as multi-user.target or graphical.target) and manages services via structured configuration files called unit files (.service), typically stored in /lib/systemd/system/ and /etc/systemd/system/.

Boot Performance and Concurrency

The primary operational difference during boot is execution strategy:

  • SysVinit (Sequential): Services launch one after another. If a network-dependent service takes five seconds to initialize, the entire boot process blocks until that script exits. This deterministic, single-threaded pipeline ensures predictability but results in slower boot times on modern multi-core hardware.
  • systemd (Parallel): Services are launched concurrently to maximize CPU and I/O throughput. systemd solves dependency bottlenecks through socket activation: standard sockets for services like D-Bus or logging are created first, buffering incoming requests while the actual daemon processes initialize in parallel in the background.

Process Tracking and Reliability

Process supervision highlights another major technical divide:

  • PID Files in SysVinit: SysVinit relies on daemons writing their process IDs (PIDs) to flat files (e.g., /var/run/daemon.pid). If a daemon crashes, double-forks, or fails to clean up its PID file, the init system loses track of the process. Child processes spawned by the service can easily become orphaned.
  • Linux cgroups in systemd: systemd uses Linux Control Groups (cgroups) to track every process spawned by a service. Even if a process forks multiple times or attempts to detach from its parent, it remains inside its designated cgroup. This guarantees reliable lifecycle management and allows systemd to terminate all sub-processes cleanly when a service stops.

Service Configuration and Management

Day-to-day administration differs significantly in syntax and structure:

  • SysVinit: Controlled via commands like service apache2 start or /etc/init.d/apache2 start. Configuring new services requires writing boilerplate Bash scripts that parse start, stop, restart, and status arguments manually.
  • systemd: Controlled uniformly via systemctl (e.g., systemctl start apache2.service). Configuration is declarative, using key-value pairs in .service files. Features such as automatic restarts, resource limits (MemoryMax), and security sandboxing (ProtectSystem, PrivateTmp) can be defined in a few lines without scripting.

Debian's Transition and Backward Compatibility

Debian officially made systemd the default init system starting with Debian 8 (Jessie), while maintaining support for alternative inits. To prevent breaking legacy packages, Debian's systemd implementation includes systemd-sysv-generator. This component dynamically reads traditional /etc/init.d/ scripts at boot and converts them into transient systemd units, allowing legacy packages without native .service files to function seamlessly within a systemd-managed environment.
