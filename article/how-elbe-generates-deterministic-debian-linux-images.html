How ELBE Generates Deterministic Debian Linux Images

This article explains how the Embedded Linux Build Environment (ELBE) leverages Debian’s binary package ecosystem and virtualization to produce deterministic, reproducible embedded Linux images. By utilizing a single declarative XML file, isolated virtual build environments, fixed Debian package archives, and automated filesystem generators, ELBE ensures that embedded system images remain strictly reproducible over long product lifecycles without relying on host-system dependencies.

Declarative Specification via a Single XML File

At the core of ELBE's deterministic model is a central sysconfig.xml file. This document acts as the single source of truth for the entire build process. It explicitly defines:

  • The exact Debian distribution and suite (e.g., Bookworm, Bullseye).
  • The package repositories and specific repository mirrors used.
  • The explicit list of target packages to install.
  • Partition layouts, bootloader configurations, and output image formats.
  • User accounts, system credentials, and custom file overlays.

Because all parameters are centralized in a machine-readable format, the build specification is easily version-controlled with tools like Git, ensuring that any build can be linked to an exact configuration state.

Host Isolation Using the Initvm

A common cause of non-deterministic builds is leakage from the host operating system, such as differing toolchain versions, missing utilities, or unique environment variables. ELBE completely eliminates this variable by using a dedicated virtual machine called the Initvm.

When an image build is requested, ELBE launches or creates an Initvm using QEMU/KVM running Debian. All image creation steps, package resolutions, and script executions occur strictly inside this isolated virtual environment. As a result, running the same ELBE build on different developer workstations, continuous integration (CI) runners, or host distributions produces identical results.

Pinning Debian Package Repositories

Unlike source-based embedded build systems such as Yocto or Buildroot, ELBE is package-based. It builds targets using pre-compiled Debian .deb packages. To achieve determinism when pulling from online repositories, ELBE provides mechanisms to lock dependencies:

  1. Snapshot Repositories: ELBE can point directly to Debian's official snapshot service (snapshot.debian.org), locking package states to a specific timestamp down to the second.
  2. Pinned Package Versions: The configuration file can pin explicit versions of packages to avoid pulling unexpected minor updates.
  3. Source and Binary Archiving: During the build, ELBE can download and bundle all consumed binary .deb packages and source packages into a local repository (such as an ISO or mirror directory). Subsequent rebuilds can target this cached, offline archive rather than dynamic remote mirrors, guaranteeing that identical package binaries are injected every time.

Target Construction and Chroot Execution

Inside the Initvm, ELBE creates the target root filesystem using standard Debian mechanisms such as debootstrap or multistrap. Because foreign architectures (e.g., ARM64, RISC-V) often need to be built on an x86_64 host, ELBE uses QEMU user-mode emulation combined with binfmt_misc.

This setup allows target architecture pre- and post-installation maintainer scripts (preinst, postinst) to execute directly in the target root filesystem context. Configuration steps run in a clean, predictable order identical to an on-device package installation.

Deterministic Filesystem and Artifact Generation

After populating the root filesystem, ELBE constructs final binary artifacts—such as raw disk images, ext4 partitions, or bootable SD card layouts—using fixed, scripted generation routines:

  • File Attributes and Timestamps: Custom files added through the XML configuration (finishing steps) are applied with defined file ownership, permissions, and timestamps.
  • Partition Generation: Partition tables (GPT or MBR) and file systems are constructed inside virtual loop devices using precise block counts defined in the XML.
  • License and SBOM Generation: As a side-effect of using the Debian packaging infrastructure, ELBE extracts the complete package manifest, software licenses (copyright files), and source code packages, generating a verifiable Software Bill of Materials (SBOM) corresponding directly to the binary output.

By combining the immutability of Debian snapshot packages, virtualization-level isolation, and declarative image authoring, ELBE produces reliable, production-ready embedded Linux platforms that can be reproduced years after initial deployment.
